# Data format

This document explains how Eonmark's game data is authored: where the files live, the unit conventions, the `Modifier` type that expresses every tech and faction effect, the integer income model, how unknown fields are rejected and how `sim-cli data-check` reports problems. It is the overview. The authoritative, field-by-field schema and the worked authoring example live in `data/rules/README.md`; where this document and that README disagree, the README wins. The Rust schema is `crates/rules/src/lib.rs`.

## Principles

- Every gameplay number is RON under `data/`. There are no tuning constants in Rust. If a value is needed and no field exists, add the field, a `data-check` rule and a line in `data/rules/README.md`.
- Integers only. The `rules`, `sim` and `ai` crates ban `f32` and `f64` through `clippy.toml`, so a RON float literal has nowhere to go and fails to parse.
- Distances are tiles, in fields ending in `_tiles`. One tile is one metre in the renderer and `Fx::ONE` in the sim.
- Fractional tiles and rates are scaled integers, with the scale in the field name: fields ending in `_x100` hold hundredths (`speed_tiles_per_s_x100: 180` is 1.8 tiles per second, `radius_tiles_x100: 35` is 0.35 tiles). The sim converts them to `Fx` exactly once; speeds become tiles per tick (`x100 / (100 * tick_rate_hz)`) at spawn. The validator caps every `_x100` field at `100000` (`rules::units::MAX_X100`).
- Durations are authored in deciseconds, in fields ending in `_ds`. The one conversion is `Rules::ticks_from_ds`: `ticks = round(ds * tick_rate_hz / 10)`, rounding to nearest with halves up. At 20 Hz one decisecond is exactly two ticks: `32` ds is 64 ticks, `600` ds is 1200 ticks. The validator does not require a whole tick count; pick values that give one when you can. The exceptions are `tick_rate_hz` and `cmd_delay_ticks` in `rules.ron`, which define the clock itself.
- Conversion happens in one place. Authored values stay in `Rules` as integers; the sim reads them only through tick and `Fx` accessors such as `Rules::attrition_interval_ticks()` and `Rules::annexation_ticks()`, which call `Rules::ticks_from_ds`. No other code converts.
- Rates are per 30 seconds. "10 Grain per 30 s" is written as `10` in a field documented as per-30-s.
- `rules_version` is a human label bumped when golden replays regenerate; `rules_hash` is computed over everything `Rules::load` reads (match rules, resources and every map at M0; `units.ron` from M1; `buildings.ron` from M3a; `techs.ron`, `ages.ron` and `factions.ron` from M4a; `data/ai/` from M5b, its `difficulty/` levels from M6) except `visuals.ron`, which `Rules::load` reads and validates but, since `rules_version` 25, does not hash (from M2 to `rules_version` 24 it did; [ADR 0003](adr/0003-visuals-outside-rules-hash.md)). Both go into every replay header. See [DETERMINISM.md](DETERMINISM.md).

## The `Modifier` type

Every tech and faction effect is a row of this shape (M4a, `crates/rules/src/modifiers.rs`), in the `modifiers` list of a tech in `techs.ron` or a faction in `factions.ron`:

```ron
(target: YieldCap, op: Mul, value: 1250)
```

| Field | Type | Meaning |
|---|---|---|
| `target` | `StatPath` | A closed enum of stats the effect may touch: `YieldCap`, `PopCap`, `TownLimit`, `TownBorderRadius`, `ResearchCost`, `ResearchTime`, `UnitHp(sel)` and `UnitDamage(sel)`, where `sel` is `Military`, `Class(<UnitClass>)` or `Kind("<unit id>")`, and from M5a `HarryingLevel` (the attrition level a player's borders impose: base 0, each Harrying tech `Add 1`, at most 8 in the worst case). A name that is not in the enum fails to parse, naming the file, the span and `StatPath` or `UnitSel`. |
| `op` | `Set`, `Add` or `Mul` | How the value combines with the base. |
| `value` | `i32` | For `Set` and `Add`, an absolute amount in the stat's own unit. For `Mul`, a permille multiplier: `1000` is unchanged, `1250` is x1.25, `900` is x0.9. |

Resolution order is `Set`, then `Add`, then `Mul`, in integer math, flooring after each `Mul` row:

```
v = the last Set in collection order, else the base
v = v + sum(Add)
for each Mul row m, in collection order:  v = floor(v * m / 1000)
```

Collection order is the faction's rows, then each researched tech in `TechId` order with its rows in file order. Flooring after each row is what makes Letters stack as 0.9, 0.81, 0.729 of the base, each floored: 100 becomes 90, 81, 72, and 150 becomes 135, 121, 108 (one floor over 0.729 would give 109).

| Base | Set | Add | Mul (permille) | Result | Note |
|---|---|---|---|---|---|
| 70 | none | none | 1250 | 87 | `70 * 1250 / 1000 = 87.5`, floored |
| 70 | none | +10 | 1250 | 100 | `(70 + 10) * 1250 / 1000 = 100` |
| 70 | 100 | +10 | none | 110 | `Set` replaces the base first |
| 100 | none | none | 1100, 1100 | 121 | `100 * 1100 / 1000 = 110`, then `110 * 1100 / 1000 = 121` |

`data-check` rejects a non-integer value (`1.25` cannot parse as `i32`, so the error names the file and the span), a `Mul` outside `1..=100000`, an `Add` or `Set` outside `±1000000` and a `Kind` selector that names no unit kind. It also bounds the worst case of every stat over every research order, so the sim's checked math cannot overflow and a Town radius stays within 64 tiles.

## Income in micro-units

Income is exact by construction. For each `(player, resource)` the sim holds an `i64` accumulator `acc`.

```
acc += min(sum_rate_per_30s, yield_cap)      every tick
stockpile += acc / 600
acc %= 600
```

At 20 Hz, 30 seconds is 600 ticks, so a rate of `r` per 30 s adds exactly `r` to the stockpile every 600 ticks with no rounding drift.

| Tick | rate | acc before | acc after `+=` | stockpile `+=` | acc after `%=` |
|---|---|---|---|---|---|
| 1 | 10 | 0 | 10 | 0 | 10 |
| 60 | 10 | 590 | 600 | 1 | 0 |
| 120 | 10 | 590 | 600 | 1 | 0 |
| 600 | 10 | 590 | 600 | 1 (total 10) | 0 |

The Yield Cap is applied to the rate before accumulation, so production above the cap is discarded and the HUD readout turns amber (M3b). Lore is exempt from the Yield Cap and has its own stockpile cap of 999. The cap is data: the base 70 is `yield_cap_base` in `rules.ron`, and the Trade techs' `YieldCap Set` rows in `techs.ron` raise it to 100, 150 and 200.

## Schema strictness

Every struct in `crates/rules` is `#[serde(deny_unknown_fields)]`. A misspelled or obsolete field fails to load with the file path and field name. New optional fields use `#[serde(default)]` so existing data keeps loading. Files other than `rules.ron` (`resources.ron`, `units.ron`, `buildings.ron`, `techs.ron`, `ages.ron`, `factions.ron`, `visuals.ron`, every map under `maps/`, from M5b `ai/personalities.ron` and every `ai/build_orders/*.ron`, and from M6 every `ai/difficulty/*.ron`) are parsed separately and attached to the `Rules` struct by `Rules::load`, so one struct carries everything and `rules_hash` covers it all but `visuals.ron`: `Rules::visuals` is `#[serde(skip)]`, so the look data is validated with the rest and left out of the hash ([ADR 0003](adr/0003-visuals-outside-rules-hash.md)).

Cross-reference checks run after parsing. Implemented as of M3a: every cost, yield and gather entry names a resource id; every unit's `trainer` names a building kind and every unit has a visual; every building's gather `worker` names a unit kind; each resource's `gathered_from` equals the building kinds that yield or gather it (checked both ways); exactly one building kind is the Town; `standard_start` names known units and lists every resource; every map start fits the Town footprint, in bounds and all grass. Added in M4a, with the `ages.ron` references resolved first so a removed tech is reported where `ages.ron` names it: every id an age unlocks exists and every unit kind, building kind and tech is unlocked by exactly one age, never before its trainer, host, predecessor level or `requires_tech`; age gates are monotonic and reachable; each tech line's levels come in order; a tech's host and a unit's `requires_tech` exist; every `Modifier` target is a valid `StatPath` with integer values and `Mul` in permille; tech and age costs fit the capped stockpiles; every attack lasts at least one tick and every hit does at least 1 damage; and every stat's worst case fits its type. Added in M5a: the age gates count only the techs that count toward an age (`counts_toward_age`, so not the Harrying side techs); `harrying_bonus_age` names an age; every `Kind` in `annexation_attackers` and `annexation_defenders` names a unit kind, each list reaches at least one kind and no attacker selector reaches a `Civilian` kind; the `HarryingLevel` rows reach at most level 8 and the attrition interval halved per level above 1 stays at least one tick; and the Town kind never has `stays_on_annexation`. Added in M5b, for the bot data under `data/ai/` (`crates/rules/src/ai.rs`, loaded last, after the maps): a build order's `id` equals its file stem and it has 1 to 64 steps; every kind, tech, age and resource id resolves; counts are 1 to 200; a `Workers` split is non-empty, names resources the worker kind gathers and sums to at most the count; `Expansion` places only the Town kind, `Terrain` only kinds with `Adjacent` slots and `BorderEdge` only kinds with `border_radius_tiles`; and static reachability: a `Build`, `Train` or `Research` step that is not unlocked by the start age or an earlier `Advance`, whose trainer or host no earlier non-optional step builds, whose prerequisite (a line's lower level, a unit's `requires_tech`) no earlier non-optional step researches, or whose count exceeds `max_per_town` times the Towns the earlier steps build, must be `optional: true`; an `Advance` is never optional, its ages go up, and the earlier non-optional steps must research its `techs_required` counting techs. Each personality has a unique id and an existing build order, a cadence in ticks above `cmd_delay_ticks`, caps of 1 to 64, radii of 1 to 64 tiles, times up to 72000 ds, an army mix of armed non-civilian kinds with weights of 1 to 1000, a `supply_kind` that `supplies`, wave sizes from 0 ds with strictly increasing times and non-decreasing sizes up to `max_wave_units` (at most 64, which bounds the bot's hashed memory), and a `wave_requires_age` that is `None` or an age. Added in M6: every build order builds a trainer of an armed kind (such as a Muster Hall) in a non-optional step before its first `Advance`; every difficulty level under `data/ai/difficulty/` has an `id` equal to its file stem, never `passive`, and a non-empty name, a `standard` level exists, its `income` names resource ids with amounts of 0 to 500, `income_interval_ds` is 0 or 50 to 72000 and in ticks more than `cmd_delay_ticks`, `income_from_ds` and `first_raid.by_ds` are below `match_cap_ds`, the multipliers are 250 to 4000 per mille, `max_wave_units` is 1 to 64, an `Age(..)` gate names an age, and a `first_raid` has `1 <= min_armed <= max_armed <= 64` and `prep_ds < by_ds`, and `worker_target_permille` is 500 to 1000; since the M6 retune (owner decision 12) a level's `pressure` block has `reinforce_min_units` and `home_guard_units` of 0 to 64, `commit_ds` and `lure_ds` of 0 to 72000, `retreat_ratio_permille` 0 to 4000, `retreat_cooldown_permille` 250 to 4000, `cohesion_tiles` 0 to 64 and `launch_ratio_permille` and `assault_ratio_permille` 0 to 10000, and its `extra_research` names at most 8 techs, each once. M6's slice 2 adds the personality knobs of retreat, raids, influence, counters, the defence and the noise: `wave_requires_tech` names a tech, raid sizes are 1 to 64 with `raid_min_armed <= raid_max_armed`, times are up to 72000 ds and radii 1 to 64 tiles, per-mille shares stay in their ranges (counter factors 0 to 8000 with floor <= 1000 <= join <= cap, noise up to 500), `counter_kinds` are armed non-civilian kinds listed once, the influence cell is 1 to 16 tiles and its radius 0 to 8 cells, and `noise_site_top_k` is 1 to 8. The field-by-field list is in `data/rules/README.md` and `data/ai/README.md`.

## How `data-check` reports errors

```bash
cargo run -p sim-cli -- data-check data/
```

Exit code 0 prints one line such as `OK rules_version=30 rules_hash=0x<16 hex> resources=4 units=8 buildings=8 ages=3 techs=12 side_techs=2 factions=1 personalities=4 build_orders=4 difficulties=3 maps=plains_1v1 strings=en visuals=units:8 buildings:8 terrain:3 models=36` (`techs` counts the techs that count toward an age and `side_techs` the rest, from M5a the Watchtower's Harrying I and II; `personalities` and `build_orders` count the bot data under `data/ai/`, from M5b, and `difficulties` its levels, from M6; the hash changes whenever any hashed file changes; M1 added `units.ron` to it, M2 `visuals.ron`, M3a `buildings.ron`, M4a `techs.ron`, `ages.ron` and `factions.ron`, M5b `data/ai/`, and `rules_version` 25 took `visuals.ron` out again (ADR 0003); the M3b UI strings and `visuals.ron` are checked but not hashed; since the art pass `visuals=` counts the unit and building entries and the dressed terrains of `visuals.ron`, and `models=` the distinct glTF files its Scenes name, each of which must be a file under the assets directory: `--assets <dir>` (default `<data>/../assets`, the repository's `assets/`), or `--no-assets` to skip the check, which appends ` (files not checked: --no-assets)`; a missing file is an `Invalid` error naming `visuals.ron`, the field and the path, such as `` data/visuals.ron: buildings["town"].path: "models/x.gltf" is not a file under assets ``). Exit code 1 prints one line starting with `error:` in one of three shapes, from `rules::Error`:

| Variant | Format | Example cause |
|---|---|---|
| `Io` | `<path>: <os error>` | File missing or unreadable |
| `Parse` | `<path>: <line>:<col>-<line>:<col>: <parser message>` | Unknown field, wrong type, RON syntax; for example `` data/rules/rules.ron: 8:3-8:18: Unexpected field named `tick_rate_hertz` in `Rules`, expected one of `rules_version`, `tick_rate_hz`, ... instead `` (ron 0.12 wording) |
| `Invalid` | `<path>: <field>: <message>` | Parsed fine but failed a range or cross-reference rule, for example `tick_rate_hz: must be > 0` |

The same loader runs at game start, so a broken file is caught before a window opens. CI runs `data-check` in the headless job on every PR.

## Changing the bot's data (M5b)

`data/ai/` is in `rules_hash` like every other loaded file but `visuals.ron`, so an edit to a build order, a personality or (M6) a difficulty level takes the data-only path of [../CONTRIBUTING.md](../CONTRIBUTING.md) ("The data-first path"): edit, bump `rules_version`, `data-check`, `just rerecord`, run the tests, and compare the bot with `sim-cli play-bots` (plus `scripts/check_first_wave.sh` for the first wave). `just rerecord` rewrites every fixture's header. A fixture's `.hash` changes only when the edit changes a decision of a bot that the fixture seats: today that is `m5_first_match` alone (the Standard bot in both seats, at the `standard` difficulty), so an edit to `standard.ron`, the `standard` row or `difficulty/standard.ron` usually moves its hash, while a new build order or personality that no fixture seats moves none. `data-check` rejects a build order the bot could never finish (the static reachability checks above) before any game runs. A new kind of step, placement or knob is a Rust change in `crates/rules/src/ai.rs` (schema and validator) and in `crates/ai`; when it can alter a decision of the shipped bot it also bumps `SIM_VERSION` (M5b owner decision 2).

## Adding a field

1. Add the field to the struct in `crates/rules/src/lib.rs` with `#[serde(default)]` if existing files must keep loading.
2. Add a validation rule if the field has a range or references another id.
3. Add the value to the RON file in authored units (tiles, deciseconds with `_ds`, per-30-s rates, permille).
4. Convert once in `crates/rules`: durations through `Rules::ticks_from_ds` behind an accessor such as `attrition_interval_ticks()`; expose ticks, `i32`, `i64` or `Fx` to the sim.
5. Document the field in `data/rules/README.md`.
6. Run `cargo run -p sim-cli -- data-check data/` and `cargo test -p rules`.
7. If the change alters simulation results, bump `rules_version` and regenerate fixtures in the same commit.
